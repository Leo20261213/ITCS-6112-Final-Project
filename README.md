This is our collaboration for our final project in Software Systems Design and Implementation Capstone Course

## Help Desk System with AI Enhancements — Sprint 3 (final) increment

### Sprint 1: secure foundation and core ticket lifecycle

| Story | Description | Where it lives |
|-------|-------------|----------------|
| US-01 | Secure login | `backend/app/routers/auth.py`, `backend/app/security.py` (PBKDF2 password hashing, expiring JWTs, lockout after 5 failed attempts) · `LoginPage.jsx`, `RegisterPage.jsx` |
| US-02 | Role-based access (admin) | `require_roles()` in `security.py`, `backend/app/routers/admin.py` · route guards in `App.jsx`, Users & roles tab in `AdminPage.jsx` |
| US-03 | End user submits a ticket | `POST /api/tickets` · `NewTicketPage.jsx` |
| US-04 | End user views own tickets | `GET /api/tickets` (scoped to the owner) · `MyTicketsPage.jsx`, `TicketDetailPage.jsx` |
| US-05 | Categories, priorities, statuses | `models.py` enums + `Category` table, admin category management, filters in `TicketTable.jsx` |
| US-06 | Agent views assigned tickets | `GET /api/tickets` (scoped to the assignee) · `AgentQueuePage.jsx` |
| US-07 | Agent updates ticket status | `PATCH /api/tickets/{id}/status` with validated transitions · status panel in `TicketDetailPage.jsx` |

### Sprint 2: ticket operations and communications

| Story | Description | Where it lives |
|-------|-------------|----------------|
| US-08 | Manager assigns tickets to agents | `PATCH /api/tickets/{id}/assignment`, `GET /api/agents` (active workload) · `ManagerPage.jsx`, `AssignmentBoard.jsx`, assignment panel in `TicketDetailPage.jsx` |
| US-09 | Users and agents exchange messages | `GET/POST /api/tickets/{id}/messages` (`routers/conversation.py`) · `TicketConversation.jsx` |
| US-10 | End user edits eligible ticket details | `PATCH /api/tickets/{id}`: title, description, category and priority only, while the ticket is Open or On hold; other fields are rejected · edit form in `TicketDetailPage.jsx` |
| US-11 | Agent closes or reopens tickets | Status transitions in `routers/tickets.py`: any non-closed ticket can be closed; Resolved/Closed tickets reopen to Open · Close/Reopen buttons in `TicketDetailPage.jsx` |
| US-12 | Ticket activity history | `GET /api/tickets/{id}/history`, recorded by `activity.record()` · `TicketHistory.jsx` |
| US-13 | Attach files to a ticket | `routers/attachments.py` (type allow-list with content check, 5 MB per file, 10 per ticket, access-checked downloads) · `TicketAttachments.jsx` |
| US-14 | Notifications about ticket updates | `routers/notifications.py`, generated by `activity.record()` for the requester and assigned agent (never the person who acted) · bell in `NotificationBell.jsx` |

### Sprint 3: AI assistance, analytics, and administration

| Story | Description | Where it lives |
|-------|-------------|----------------|
| US-15 | AI suggests a ticket category | `POST /api/tickets/{id}/ai/triage` (`ai/service.py: triage`) · AI triage panel in `AiTriagePanel.jsx`; the agent applies it with `PATCH /api/tickets/{id}/classification` |
| US-16 | AI flags urgency and suggests a priority | Same triage request: suggested priority, quoted urgency signals, confidence and reason |
| US-17 | AI summary of a ticket conversation | `POST /api/tickets/{id}/ai/summary` · "Summarize with AI" in `TicketConversation.jsx` |
| US-18 | AI reply drafts the agent edits before sending | `POST /api/tickets/{id}/ai/reply` (optional guidance) · "Draft with AI" fills the reply box; nothing is sent automatically |
| US-19 | End-user help chatbot | `POST /api/assistant/chat`, answers only from approved articles (`help_content.py`) and hands off to a prefilled ticket when unsure · `AssistantPage.jsx` (Help assistant) |
| US-20 | Analytics dashboard | `GET /api/analytics?days=7/30/90` (`routers/analytics.py`) · `AnalyticsDashboard.jsx` (admin Analytics tab, manager Analytics page) |
| US-21 | Administrators configure AI | `GET/PUT /api/admin/ai-settings`, `GET /api/admin/ai-usage` · `AiSettingsPanel.jsx` (admin AI settings tab) |

**How the AI works.** AI features call Claude (`claude-opus-5-5` by default) through the official `anthropic` Python SDK, using structured JSON output so every answer is validated before it is shown. To enable Claude, set `ANTHROPIC_API_KEY` in the backend's environment before starting it. Without credentials, or if Claude fails, the app uses built-in keyword rules instead, so every feature still works offline. Every result is labelled with what produced it.

Responsible-AI controls (US-21):
- An administrator can turn AI off as a whole or per feature.
- The provider can be set to Claude with fallback, Claude only, or built-in rules only.
- The administrator picks the Claude model and can add guidance for reply drafts.
- By default, names, email addresses and phone numbers are removed before ticket text is sent to Claude.
- Ticket text is passed to Claude as data, and instructions inside it are ignored.
- Agents always decide whether to apply a suggestion or send a draft.
- Each AI request is logged (feature, user, provider, outcome, latency; never the content).

Roles: **end user** (submits, tracks, edits and discusses their tickets; uses the help assistant), **support agent** (works their assigned queue, closes and reopens tickets), **manager** (sees every ticket, assigns it to agents, and views analytics), **administrator** (views analytics; manages users, roles, categories and AI settings; can also assign tickets).

New tickets are still routed automatically to the active agent with the fewest active tickets; managers can reassign them from the assignment board. Closed tickets are read-only (no new messages or attachments) until an agent reopens them.

Attachments are stored on disk in `backend/uploads/` (override with `UPLOAD_DIR`; per-file limit with `ATTACHMENT_MAX_MB`). Allowed types: png, jpg/jpeg, gif, webp, pdf, txt, log, csv, docx, xlsx.

### Running locally

Prerequisites: Python 3.11+, Node 18+, and Docker Desktop (for the PostgreSQL database).

**Database** (PostgreSQL 17 in Docker, on host port 5433 so it doesn't clash with a locally installed PostgreSQL on 5432):

```bash
docker compose up -d db        # builds the image from ./db on first run
```

The image (`db/Dockerfile`) creates the `helpdesk` database and user, sets the time zone to UTC, and also creates a `helpdesk_test` database for running the tests against PostgreSQL. The password defaults to `helpdesk` for development; set `POSTGRES_PASSWORD` (and `POSTGRES_PORT`) in your shell or a `.env` file next to `docker-compose.yml` to change it. Data persists in the `pgdata` volume. `docker compose down -v` deletes it.

**Backend** (http://127.0.0.1:8000, interactive API docs at `/docs`):

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env          # macOS/Linux: cp .env.example .env
uvicorn app.main:app --reload
```

`backend/.env` sets `DATABASE_URL=postgresql://helpdesk:helpdesk@localhost:5433/helpdesk` (and optionally `ANTHROPIC_API_KEY`). Without `DATABASE_URL` the backend falls back to a local SQLite file.

To use Claude for the AI features, put `ANTHROPIC_API_KEY=sk-ant-...` in `backend/.env` (or set it in your shell) and restart the backend.

**Frontend** (http://localhost:5173, proxies `/api` to the backend; set `API_URL` to use a backend on another address):

```bash
cd frontend
npm install
npm run dev
```

The first time the backend starts against an empty database, it creates the tables and loads demo data. Every demo account uses the password `Password123!`:

| Role | Email |
|------|-------|
| Administrator | admin@helpdesk.local |
| Manager | manager@helpdesk.local |
| Support agent | agent1@helpdesk.local, agent2@helpdesk.local |
| End user | user1@helpdesk.local, user2@helpdesk.local |

To start over with fresh demo data, run `docker compose down -v` then `docker compose up -d db` (with SQLite, delete `backend/helpdesk.db`), and delete `backend/uploads/`. Set `SEED_DEMO_HISTORY=0` to skip the past tickets. Set `SECRET_KEY` in the environment to keep users signed in across restarts; without it, a random key is generated on each start.

### Tests

```bash
cd backend
pytest
```

The tests run on a throwaway SQLite file by default. To run them against PostgreSQL:

```bash
set TEST_DATABASE_URL=postgresql://helpdesk:helpdesk@localhost:5433/helpdesk_test   # macOS/Linux: export ...
pytest
```

The tests use the built-in AI rules and a stand-in Claude client, so they never call the real API.

17 acceptance tests in `backend/tests/test_sprint1.py` cover US-01 through US-07, including the authorization cases: users can't see other users' tickets, agents can't update tickets they aren't assigned, and non-admins can't use admin endpoints.
